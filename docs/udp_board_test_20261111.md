# UDP 实板测试记录

日期：2026-11-11。工作目录：`E:\AMY_ALL_CODE\ad_one_channel`，分支：`udp_client`。

## 连接异常根因

板子配置：设备 ID=3，本机 `192.168.10.100`，网关 `192.168.10.1`，服务器 `49.239.193.149:9000`。
电脑网卡同时有 `192.168.10.1/24` 和 `49.239.193.149/32`。

旧 Bridge 监听 `0.0.0.0:9000`。板子注册能到电脑，但 Windows 从 `192.168.10.1:9000`
发回 GET_PARAM，而不是从板子配置的 `49.239.193.149:9000` 回包。
板端连接式 UDP PCB 正确拒绝不匹配的远端来源，因此不断打印注册和 Peer timeout。

实板 Ethernet RX_POOL 快照确认了上述源 IP、端口和有效命令内容，证据：
`build/live-diagnostics/udp_rx_pool_before.bin`。这次故障不是由 LAN8720A 链路协商失败引起。

本次故障修复没有额外修改固件生产代码。先前 UDP 迁移代码仍保留。
未修改电脑 IP、防火墙或网卡驱动，也未覆盖原 TCP 上位机源文件及 EXE。

## 实测结果

测试为板子与本机直连以太网，使用电脑上的公网 IP 别名，并非真实公网或 5G 链路。
接收脚本连接同一个 Bridge 的本机 TCP 9001，只读取真实板端帧并发送协议命令，不生成样本。

| 项目 | 结果 |
| --- | --- |
| 绑定地址后 GET_PARAM | 收到成功 ACK，单次响应约 1.55 ms |
| 400k 档、24 位首轮 12 秒 | 4,647,188 样点，CRC/缺口/倒序均为 0 |
| 400k 档、24 位最终 20 秒 | 7,773,600 样点，23,320,800 字节原始样本，平均约 1.166 MB/s |
| 最终 24 位数据完整性 | CRC 错误=0，样点缺口=0，倒序=0，板端 overrun=0 |
| 400k 档、16 位约 8 秒 | 3,092,672 样点，CRC/缺口/倒序均为 0，板端 overrun=0 |
| STOP | 成功回执，running=0，ready=0，free=24 |

400k 是配置档位名；外部 25 MHz ADC 时钟下，DATA meta 如实报告实际 `390625 S/s`，
不是精确的 400000 S/s。最终 24 位样点序列跨度测得约 `390268 S/s`。
接收平均值包含 START 初始化等待和操作系统调度，不能仅凭首秒或分秒桶判断 ADC 时钟。

### 服务端中断与恢复

采集中关闭本次启动的上位机服务，等待约 35 秒：板端打印 Peer timeout，停采并重新注册。
SWD 确认 running=0、connected=0，同时保留采集请求和恢复标志；未观察到 HardFault。

重启修复版 EXE，故意不传 `--bind-ip`，验证沿用已保存地址。
Bridge 实际监听 `49.239.193.149:9000`，本机 GUI 自动接入 TCP 9001。
不再发送 START，只查询状态，随后重新收到采样 DATA，证明自动续采路径生效。

该 10 秒恢复窗口包含约 3 秒等待，收到 1,849,008 样点，CRC/缺口/倒序为 0；
此窗口采样序列跨度速率约 293250 S/s，只用于恢复功能验证，不作为满速依据。
随后重新设置原参数并 START，最终 20 秒复测达到上表速率。

没有进行物理拔插网线测试；模拟链路状态变化由状态机测试覆盖，不能称为实板拔插通过。
